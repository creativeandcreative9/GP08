# GP08 全体計画（2026-10-16 時点）

鎌倉風の日本の街（桜・海・山）でのんびり暮らす、ブラウザ向け 3D ライフシミュレーションゲーム。
Babylon.js 9 + Vite + TypeScript。主人公は開発時に非公開MMDモデル（吹雪）、公開版ではオリジナルの手続き生成キャラクター。

この文書は「どこへ向かうか」と「どの順に進めるか」をまとめる。作業の細かい状態と再開方法は
`docs/20261016_handover.md`（引き継ぎ書）、見た目の採点基準と記録は `docs/20261016_visual_eval.md` を見る。

## 1. 目標

1. **見た目**：ユーザーが示した参考画像（春の日本の街を目線の高さで描いたアニメ調 3D 映像、5 枚）と同等の見た目にする。
   採点は `docs/20261016_visual_eval.md` のルーブリック（10 項目 × 10 点、参考画像＝100 点）で数値化する。
2. **歩いて楽しい街**：駅・商店街・住宅街・路地・公園・海・山を、主人公が歩いて見て回れる。表通りの密度と、路地や空き地の「抜け感」「裏道感」の両方がある。
3. **ライフシミュレーション**：時間の流れ、店や家に入る、人と話す、物を買う、などの「暮らし」の要素（段階 2 以降）。

## 2. 方針

- 町は**完全に手続き生成**。画像ファイルを持たず、形はコード、質感はシェーダー（`src/surface.ts`）とキャンバスで描く動的テクスチャで出す。乱数は種付き（同じ町が毎回できる）。
- **モデル（MMD）は非公開リポジトリ GP08-assets だけで扱う**。公開リポジトリにはコミットしない（CLAUDE.md 参照）。
- 画質は `?gfx=high`（影・SSAO・ブルーム・色調整）と `?gfx=low`。GPU のない環境は自動で low。
- 見た目の変更は毎回 `npm run eval` で比較カット 5 枚を撮り、ルーブリックで採点して記録する。
- 実装は並列の作業担当（AI エージェント）に分け、統合・採点・難所（描画、シェーダー）はまとめ役が持つ（引き継ぎ書の「進め方」）。

採点（参考画像＝100 点）：ベースライン r0 = **20.8 点**、ラウンド 1 後 r1 = **約 50 点**（詳細は評価ドキュメント）。

### ラウンド 1（完了）

### ラウンド 2（途中で中断：引き継ぎ書の WIP を参照）
1. **人と車**：歩行者・立ち止まる人・座る人・店員・犬の散歩、駐車と走行の車は統合済み。人物と車の形・素材の仕上げは残る。段階2ではこの住人を使って会話とおつかいを実装。
2. **植生**（植生と桜 2.5 → 目標 7 以上）：花びらの絵を貼った板（スプライト）で桜の樹冠を「柔らかい花の雲」にする。生け垣・花壇・草・ツタ・他の街路樹。
3. **建物（主役 3 店と住宅以外）**：病院・銀行・学校・中層マンション・ふつうの店の外壁の奥行き・素材・屋上。

### ラウンド 3（予定）
- 光の筋（窓から差す光、木漏れ日）、窓ガラスへの景色の映り込み
- 近景の質感をさらに上げる（看板の汚れ、壁の目地、地面の小石や水たまり）
- 遠景の扱い：建物の細部が遠くでちらつくので、距離で簡略化（LOD）する
- 性能：頂点数（現在 約 160 万）を減らす（`MeshBatch` の四角形を 4 頂点の共有にすると約 3 分の 1 減る見込み）、看板アトラスを 4096px 以内に収める
- 実機（GPU 搭載 PC・スマホ）での FPS 計測と画質の自動切り替え

### 目標点と判定
- r2 で 65 点、r3 で 80 点、最終的に 90 点以上（各項目 8 点以上）を目標にする。

## 6. リスク

- **性能**：r47の町の生成報告は約191万頂点・113万三角形で、高画質の影専用樹冠も含む。大きな花房の主画面での描画は169,416から13,032三角形へ削減し、軽量画質では影専用形状をGPUへ送らない。遠景LODと解像度調整も維持する。生成総量は実際に描く負荷やFPSとは区別し、SwiftShaderだけではスマホ実機の合否を判定しない。
- **テスト時間**：ヘッドレス環境は GPU がなくソフトウェア描画。高画質の撮影は 1 枚に数十秒〜数分かかる。
- **看板アトラス**：4096×2688pxへ修正済み。対象実機での表示・性能は引き続き確認が必要。
- **ライセンス**：MMD モデルは非商用・再配布禁止。公開ビルドに含めない。参考画像も第三者の映像なので公開リポジトリに置かない。
